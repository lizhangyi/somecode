## diary-lynx 保存 Bug 修复（Web 预览下点保存没存上）

- **根因**：`src/storage/index.ts` 原用 `typeof localStorage !== 'undefined'` 选 web/native 实现。但 ReactLynx 双线程架构下，组件逻辑（含保存事件）跑在**后台线程**——Lynx for Web 里是标准 DedicatedWorker（`@lynx-js/web-core` 的 BackgroundThread 用 `new Worker(url,{type:'module'})` 创建），该 Worker **既无 localStorage 也无 NativeModules**。于是 Web 预览误判为 Native → 选 nativeStorage → 调未注册的 `NativeModules.NativeLocalStorageModule` 抛错 → 被 setItem 的 try/catch **静默吞掉** → save 假成功、pop 返回，但数据从未落盘。
- **关键事实（查 @lynx-js/web-core 源码确证）**：框架自身跨线程通信走**独立 MessageChannel + @lynx-js/web-worker-rpc**，只挂在那条 MessagePort 上，**没在 Worker 对象挂 onmessage、不转发到 window**。所以用户态后台线程 `self.postMessage` 到不了 window；且 DedicatedWorker 场景 `MessageEvent.source` 为 null。
- **修复**：①平台检测改 `typeof NativeModules === 'undefined' ? webStorage : nativeStorage`（后台线程无 NativeModules → 正确选 webStorage）。②web.ts 用标准 **BroadcastChannel**（window 与同源 Worker 各自 `new BroadcastChannel(name)`，同源投递、不回投发送者、不依赖 event.source、独立于框架 rpc）做跨线程 localStorage 桥接；主线程注册中继代存，后台线程发请求 await 响应。③加 5s 超时兜底，setItem 跨线程路径抛错（让 .catch 接住），绝不卡死。④旧 postMessage/event.source 方案是错的（会永久 pending 卡死）。
- **测试**：53/53（新增 webTransport.test.ts 用真实 Node BroadcastChannel 验证双向 + 无传输时 reject；storageIndex.test.ts 更新为新选择逻辑）。
- **未坐实**：浏览器实跑闭环只能用户验（沙箱无浏览器自动化）。验收点：console 应见 `[diary-storage] main-thread relay ready` 与 `worker channel ready`；新建→保存→返回列表出现→刷新仍在。
- 教训：跨线程持久化别用 typeof localStorage 判平台；Lynx Web 后台线程是 Worker，用户态跨线程桥首选 BroadcastChannel。
